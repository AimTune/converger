# Converger Protocol v1 (`converger/1`)

> **Status: draft for review (#21).** Normative once merged. The protocol is a
> **superset profile of [mekik/1](https://github.com/AimTune/mekik/blob/main/PROTOCOL.md)**
> (decision recorded in #63 and [ADR-0024](../adr/0024-converger-protocol-v1-as-superset-of-mekik-1.md)):
> it is identical to mekik/1 wherever mekik/1 defines something, and additive where
> the hub needs more. The rich message vocabulary is in [messages.md](./messages.md).
> JSON Schemas (draft 2020-12) for every frame live in
> [`priv/protocol/v1/`](https://github.com/AimTune/converger/tree/main/priv/protocol/v1)
> and ship with every release.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

Every feature is marked with its status:

- **Implemented**: the server does this today.
- **Planned (#N)**: specified here, delivered by issue #N. Until then a client MUST NOT
  rely on it. Server implementation issues use the frame and field names from this document.

## 1. Model and principles

- **Persist first, then push.** Every persistent frame a client receives was derived from a
  committed activity with a `seq`. The socket is a cache of the database, never the source
  of truth.
- **One ordered log per conversation.** Persistent frames carry a 1-based, per-conversation,
  strictly monotonic `seq` with no gaps (mekik/1 section 2). A client's `watermark` is the
  highest `seq` it has durably seen. Reconnecting with a watermark replays exactly what is missing.
- **Client ids and acks** give at-least-once sending and exactly-once persistence.
- **Receivers ignore what they do not understand.** Unknown fields and unknown frame types
  MUST be ignored (mekik/1 preamble), so additive changes never break an older peer.
- **Bounded everything**: frame size, in-flight sends, replay batches, conversations per socket.

Identity (mekik/1 section 1):

| id | lifetime | meaning in Converger |
| --- | --- | --- |
| `userId` | permanent | the end user. Verified when the token carries `user_id`. |
| `conversationId` | until deleted | a Converger conversation (UUID). |
| `connectionId` | one socket | a routing handle for one live connection. |
| `watermark` | per client | the highest persistent `seq` the client has durably seen. |

A conversation may have many live connections at once (tabs, devices, agents, the bot channel).
Every persistent frame is delivered to all of them, except that a user's own turn is not echoed
to the connection that sent it (section 6.4).

## 2. Transports and version negotiation

Frames are JSON objects with a `type` discriminator, one frame per WebSocket text message,
UTF-8. Binary WebSocket messages are rejected with `error` `bad_request` until a binary
encoding is negotiated (MessagePack, **Planned (#26)**).

### 2.1 Native endpoint: **Planned (#22, #26)**

```text
wss://HOST/socket/converger/v1
```

Raw frames exactly as in this document, which makes the endpoint wire-compatible with mekik/1
clients such as `@chativa/connector-mekik`.

- A client SHOULD offer the WebSocket subprotocol `converger.v1`
  (`Sec-WebSocket-Protocol: converger.v1`). The server selects it when offered.
- A client that offers **no** subprotocol is accepted and spoken to as `converger/1` with
  mekik/1 semantics (mekik/1 defines no subprotocol). This is how unmodified mekik/1 clients connect.
- A client that offers subprotocols, none of which the server supports, is refused during the
  upgrade (HTTP 400). A future `converger.v2` is offered next to `converger.v1` (section 13).
- Identity hints MAY travel in the query string (`?conversationId=...&userId=...`) for
  sticky routing by an L7 load balancer, as in mekik/1. They are hints; `hello` and the token decide.

### 2.2 Phoenix Channels binding

```text
wss://HOST/socket/converger/websocket?token=TOKEN&vsn=2.0.0
topic: converger:conversation:CONVERSATION_ID
```

`vsn` is the **Phoenix serializer version**, not the protocol version. The protocol version is
chosen in the join payload:

- **Implemented (legacy shape):** a join without `protocol` gets the pre-v1 frames: the join
  payload may carry an opaque `watermark`; the server pushes `activitySet` events
  `{activities, watermark, has_more}` (replay, then one per live activity). See section 13.3. The client
  sends with the event `postActivity` (an activity with an optional `clientId`; the reply is `{id, seq, watermark}`
  or `{reason}`), **Implemented (#23)**; it is part of the pre-v1 shape and is replaced by v1 message frames and `ack`.
- **Planned (#22):** a join payload `{"protocol": "converger/1", ...hello fields}` switches the
  topic to v1. Every server frame is then pushed as the Phoenix event `frame` whose payload is
  the complete frame (including `type`); clients push frames with the event `frame` too. The
  Phoenix reply to a client push is only a transport receipt: the protocol answer is the `ack`
  or `error` frame. The Phoenix heartbeat (topic `phoenix`) replaces the `heartbeat`/`ping`
  frames on this binding.

### 2.3 Legacy socket: **Implemented, deprecated (#23)**

`/socket/websocket` (`ConvergerWeb.UserSocket`), topic `conversation:CONVERSATION_ID`, events
`new_activity` / `replay_truncated`, resume by `last_activity_id`, authenticated with a legacy conversation token.
It does not speak v1, logs a deprecation warning per connection and is removed according to the deprecation
policy (section 13.3). See [migrating from the legacy API](../api/migrating-from-legacy.md).

## 3. Authentication

### 3.1 Tokens

Clients authenticate with a Converger token (JWT, `type: "converger"`), issued by
`POST /api/v1/converger/tokens/generate` (channel secret) and renewed by
`POST /api/v1/converger/tokens/refresh`. **Implemented** claims:

| claim | meaning |
| --- | --- |
| `type` | always `converger` |
| `tenant_id`, `channel_id` | the channel the token belongs to; the channel must be active |
| `sub` | `converger_CHANNEL_ID` |
| `exp` | expiry; default lifetime 1800 s |
| `conversation_id` | optional: restricts the token to one conversation |
| `user_id` | optional: the verified end user; also the socket identity (`ConvergerWeb.Sockets`) |
| `scope` | **Planned (#64):** `conversation` (default) or `channel` (agent and bot-channel sockets, section 10) |

Credential sources, in order of precedence: the `Authorization: Bearer` header
(**Planned (#22)**, for non-browser clients), the `token` query parameter (**Implemented**
on the Phoenix binding), `hello.token` (**Planned (#22)**, mekik/1 section 7).

### 3.2 Identity resolution

- A verified `user_id` claim overrides any client-asserted `userId` (anti-spoofing, mekik/1).
  Without one, the server echoes the asserted `userId` (or mints one) in `welcome`; such an id
  is informational and never used for authorization.
- A `conversation_id` claim fixes the conversation; an asserted different `conversationId` is ignored.
- With a channel-level token (no `conversation_id`), an asserted `conversationId` is adopted only
  when the conversation belongs to the token's channel and tenant and, if the token carries
  `user_id`, to that user. Otherwise the server creates a new conversation, as
  `POST /conversations` does. When `welcome.data.conversationId` differs from the asserted one
  the client MUST reset its watermark to 0 (mekik/1 section 1).

### 3.3 Rejection, expiry and refresh

- **Native endpoint, Planned (#22):** a missing, invalid or expired credential, or an inactive
  channel, is answered with `error` `unauthorized` and the socket is closed with code **4401**
  (mekik/1 section 7). A client SHOULD NOT reconnect with the same credential.
- **Phoenix binding, Implemented:** the upgrade is refused (Phoenix answers HTTP 403); a join
  that is not authorized for the conversation is answered `{"reason": "unauthorized"}`.
- **Channel deactivation, Implemented:** the sockets of a deactivated channel are disconnected
  and cannot reconnect while it stays inactive. On the native endpoint this is close code
  **4403** after `error` `channel_inactive` (**Planned (#22)**).
- **Mid-session refresh, Planned (#22):** before `welcome.data.expiresAt`, a client sends
  `auth` with a fresh token whose tenant, channel, conversation and user claims match the session.
  The server answers `tokenRefreshed`. A token that does not match draws `error` `forbidden`
  and the session continues on the old token.
- **Expiry, Planned (#22):** at `expiresAt` without a refresh, the server sends `error`
  `token_expired` (retryable) and closes with **4401**. The client refreshes over REST and
  reconnects **with the same watermark**: nothing is lost because everything persistent is replayed.

## 4. Handshake

```text
client -> hello            (first frame; MAY be preceded only by nothing)
server -> welcome          (identity, head watermark, open interrupts, capabilities, limits)
server -> genui_components (relayed from the bot channel, if it defines any)
server -> skills           (relayed from the bot channel, if it defines any)
server -> replay           (every persistent frame with seq > hello.watermark, in order)
server -> live frames
```

A client SHOULD send `hello` immediately after the upgrade. Any other frame before it draws
`error` `no_session`. A second `hello` is ignored (mekik/1 section 3.1). A field of the wrong type
in `hello` is ignored as if absent. **Planned (#22).**

```json schema=frames/client/hello.schema.json
{ "type": "hello", "protocol": "converger/1", "conversationId": "c0a8012e-7d3b-4c5e-9f1a-2b3c4d5e6f70", "watermark": 12, "token": "eyJhbGciOiJIUzI1NiJ9.e30.sig" }
```

`welcome` is mekik/1's, with `protocol: "converger/1"` and `compat: ["mekik/1"]`, plus Converger
fields. `watermark` is the conversation's **head seq** at handshake time: replayed frames carry
`seq` up to it, live frames are above it. `pending` re-announces open interrupts (mekik/1 PendingView).

```json schema=frames/server/welcome.schema.json
{
  "type": "welcome",
  "data": {
    "protocol": "converger/1",
    "compat": ["mekik/1"],
    "conversationId": "c0a8012e-7d3b-4c5e-9f1a-2b3c4d5e6f70",
    "userId": "user-42",
    "connectionId": "conn-8f3a",
    "watermark": 17,
    "pending": [],
    "scope": "conversation",
    "expiresAt": 1750001800000,
    "capabilities": { "acks": true, "receipts": true, "presence": true, "typing": true, "regenerate": false, "edit": false },
    "limits": { "maxFrameBytes": 131072, "maxTextBytes": 65536, "maxMetadataBytes": 16384, "maxInFlight": 32, "heartbeatIntervalMs": 30000, "idleTimeoutMs": 60000, "replayBatch": 100, "replayMax": 10000 }
  }
}
```

`capabilities.regenerate` and `capabilities.edit` are the flags chativa's mekik connector already
reads; they are true only when the conversation's bot channel advertises them.
`capabilities.messageTypes` MAY list the message types the server will deliver natively.

## 5. Frames

### 5.1 Persistent and transient frames

A **persistent** frame is stored as an activity, has a `seq`, and is replayed. A **transient**
frame is live-only: never stored, never replayed, no `seq`.

Persistent frames come in two shapes:

1. **Message frames** (`text` and every message type of [messages.md](./messages.md), plus the
   Converger types `event` and `conversationUpdate`) use the mekik/1 `text` envelope:

   | field | type | notes |
   | --- | --- | --- |
   | `type` | string | the message type (renderer name) |
   | `id` | string | activity id (UUID minted by Converger, or the id a mekik bot supplied) |
   | `seq` | integer | 1-based, per conversation |
   | `from` | `"user"` or `"bot"` | relative to the end user. Every other party (bot, human agent, system) is `"bot"`, so chativa renders it on the correct side |
   | `data` | object | the typed payload |
   | `timestamp` | integer | ms since the epoch (UTC); the server's commit time |
   | `sender` | object, optional | Converger: `{id, role, name?}`, `role` one of `user`, `bot`, `agent`, `system` |
   | `metadata` | object, optional | Converger activity metadata (REST `channelData`), at most 16 KiB |
   | `actions` | array, optional | quick-reply chips on a bot `text` frame (chativa `parseChatFrame` rule) |
   | `clientId` | string, optional | the sender's clientId, so a sender's other connections can de-duplicate |

2. **mekik/1-native frames** (`tool_call`, `skill`, `genui`, `interrupt`, `interrupt_resolved`)
   keep exactly the mekik/1 shape. Converger adds **no** top-level fields to them, so frames relayed
   from a mekik bot round-trip byte-identically (canonical JSON, mekik/1 section 9) except for
   `seq`, which is renumbered into the conversation's seq space. They are addressed by
   `(conversationId, seq)`.

```json schema=frames/server/message.schema.json
{ "type": "text", "id": "msg-1", "seq": 17, "from": "bot", "data": { "text": "Refund complete: ORD-42" }, "timestamp": 1750000000000 }
```

```json schema=frames/server/tool_call.schema.json
{ "type": "tool_call", "seq": 12, "data": { "id": "t1", "name": "get_order", "status": "completed", "result": { "id": "ORD-42", "total": 249.9 } } }
```

### 5.3 Client to server

| `type` | schema | handled by | status |
| --- | --- | --- | --- |
| `hello` | `frames/client/hello` | server | Planned (#22) |
| `text` and message types | `frames/client/message` | persisted, then routed | Planned (#22); today REST `POST .../activities` or the pre-v1 `postActivity` event (section 2.2) |
| `resume`, `genui_event`, `client_tools`, `client_skills`, `abort`, `survey`, `regenerate`, `edit` | `frames/client/*` | forwarded to the conversation's bot channel | Planned (#64) |
| `typing` | `frames/client/typing` | relayed, not stored | Planned (#25) |
| `read` | `frames/client/read` | read receipt | Planned (#25) |
| `sync` | `frames/client/sync` | replay on a live connection | Planned (#22) |
| `ping` | `frames/client/ping` | answered with `heartbeat` | Planned (#22) |
| `auth` | `frames/client/auth` | token refresh | Planned (#22) |

The `send` frame drafted in #21 is not part of v1: a user turn is the typed message frame of
mekik/1 (`{"type": "text", "data": {"text": "..."}}`), generalised to every message type, with an
optional `clientId`. The `resume {watermark}` frame drafted in #21 is named `sync`, because
`resume` is mekik/1's interrupt answer.

```json schema=frames/client/message.schema.json
{ "type": "text", "clientId": "c-17", "data": { "text": "Where is my order?" }, "meta": { "locale": "tr-TR" } }
```

Client turn fields: `data` (typed by message type), `clientId` (section 7), `meta` (mekik/1
per-turn context, relayed to the bot channel, never stored), `metadata` (stored with the
activity), `replyTo` (the activity a tapped button answers). `id` and `timestamp`, which
chativa's `OutgoingMessage` carries, are accepted and ignored.

### 5.4 Activities as frames

Converger activities (`Converger.Activities.Activity`, canonical map in
`Converger.Activities.Serializer`) map to v1 frames as follows. **Planned (#22)**; the rich
types replace the attachment mapping with #28.

| activity `type` | frame | `data` |
| --- | --- | --- |
| `message` | `text` | `{text, attachments?}`: `text` is `""` when null; non-empty attachments are carried verbatim |
| any message type (after #28) | that type | the stored typed payload |
| `event` | `event` | `{name?, text, value?}` (for example a WhatsApp reaction) |
| `conversationUpdate` | `conversationUpdate` | the activity metadata, for example `{event: "conversation_closed", status, reason}` |
| `endOfConversation` | `conversationUpdate` | `{event: "conversation_ended", status: "closed"}` |
| `typing` | `typing` with `seq` | `isTyping: true` live, `false` on replay. Typing becomes transient with #25; frames with a `seq` exist only for typing activities persisted before that |

`activity.sender` becomes `sender.id`; `from` and `sender.role` derive from the side that
created the activity (end-user channel: `user`; bot channel: `bot`; agent console: `agent`;
lifecycle events: `system`). `inserted_at` becomes `timestamp` in milliseconds.

### 5.5 Unknown frames and reserved names

- A receiver MUST ignore unknown fields and unknown frame types (mekik/1). A server answers an
  unknown or malformed client frame with `error` `bad_request` and keeps the connection open.
- A frame type that is not a protocol frame is a **rich message frame** (mekik/1 section 4.5): the
  server persists it as an activity with `type = frame.type` and relays it without interpreting
  `data` (section 4 of [messages.md](./messages.md)).
- **Reserved frame types**, which no message may use (`text` excepted): the mekik/1 set
  (`hello welcome text resume genui_event client_tools client_skills abort tool_call skill skills
  genui genui_components interrupt interrupt_resolved run error typing`), chativa's client frames
  (`survey regenerate edit`) and Converger's (`ack deliveryStatus presence conversationUpdate
  endOfConversation event heartbeat ping read sync auth tokenRefreshed replayTruncated subscribe
  unsubscribe subscribed unsubscribed message activity activitySet frame`). The list is
  `$defs/reservedFrameType` in `common.schema.json`.

## 6. Ordering, replay and the watermark

### 6.1 seq

`seq` is allocated by the server when the activity is committed, under the conversation row
lock, so it is strictly monotonic and gap-free per conversation (**Implemented**:
`Converger.Activities`, per-conversation `seq`). Persistent frames are delivered on each
subscription in `seq` order.

### 6.2 Replay

After `welcome` the server replays every persistent frame with `seq > hello.watermark`, in order,
then switches to live delivery. Frames committed while the replay tail is read are held back and
de-duplicated, so each frame arrives exactly once and in order (mekik/1 section 2). **Planned (#22).**

- The replay is read in batches of `limits.replayBatch` (`ws_replay_limit`, default 100,
  **Implemented** as the cap of the current `activitySet` replay).
- At most `limits.replayMax` frames (default 10 000) are replayed per handshake or `sync`. Beyond
  that the server sends `replayTruncated {watermark, headSeq}` and continues live; the client fetches
  the rest with `GET /api/v1/converger/conversations/ID/activities?watermark=N` (paged by
  `has_more`, **Implemented**) or sends `sync` again.
- An absent `hello.watermark` means 0: a fresh client gets the whole transcript (bounded as
  above), as in mekik/1. The legacy Phoenix binding keeps its current behaviour (no watermark, no replay).

```json schema=frames/server/replayTruncated.schema.json
{ "type": "replayTruncated", "data": { "watermark": 10000, "headSeq": 12500 } }
```

### 6.3 Gap detection

Phoenix PubSub is at-most-once across nodes, so a live frame can be lost between nodes.

- **Server, Planned (#22):** the connection process tracks the last `seq` it pushed. A live
  frame with `seq` greater than `last + 1` makes it read the missing range from the database and
  push it first. Frames with `seq` at or below `last` are dropped as duplicates.
- **Client, SHOULD:** a client that stamps every send with a `clientId` knows every `seq` it should
  see (frames plus its own acks). On a gap it sends `sync {watermark: LAST_CONTIGUOUS}`; the server
  replays `seq > watermark` with the same hold-back rule. A client that sends without `clientId`
  (every mekik/1 client) cannot tell its own unechoed turns from a gap and simply tracks the
  highest `seq` seen, as mekik/1 does.

```json schema=frames/client/sync.schema.json
{ "type": "sync", "watermark": 15 }
```

### 6.4 Echo rule

A user's own turn is not delivered back to the connection that sent it (mekik/1 section 1); it is
delivered to the conversation's other connections, including the sender's other tabs, and replayed
on reconnect. With a `clientId` the sending connection gets an `ack` carrying the `id` and `seq`.

### 6.5 The watermark and its migration

In v1 a watermark is the **integer seq** (JSON number). This supersedes the opaque watermark of
the Converger API (#63).

| phase | server emits | server accepts |
| --- | --- | --- |
| Today (**Implemented**) | base64url of `seq:N` (`Converger.ConvergerAPI.Watermark`) | `seq:N` base64url; legacy base64url activity UUID; anything else: REST starts from the beginning, WebSocket does not replay |
| v3.0, with #22 | integer in every v1 frame and in REST `activitySet.watermark`; the legacy Phoenix `activitySet` keeps the string | integer (number or decimal string), `seq:N` base64url, legacy activity UUID |
| v3.0 + one minor release | integer everywhere | integer only; a base64url watermark draws `invalid_watermark` |

The forms cannot be confused: a decimal string is all digits, while a base64url watermark always
starts with a letter (`c2Vx...` for `seq:`, `M`, `Y` or `Z` for a UUID). The release that drops the
legacy forms is announced in the changelog one release ahead.

Invalid watermarks (**Planned (#22)**): in `hello` a watermark of the wrong type is ignored as if
absent (mekik/1). A well-formed watermark above the head is answered with `error`
`invalid_watermark` and no replay; `welcome.data.watermark` tells the client the real head, and
the client SHOULD then `sync` from its last trusted value or 0.

## 7. Sending, acks and idempotency: **Planned (#24)**

- A send MAY carry `clientId` (1 to 128 characters of `A-Z a-z 0-9 . _ : ~ -`, unique per
  conversation and sender, for example a UUID or a counter prefixed with a session id).
- The server persists the activity, then sends `ack {clientId, id, seq, timestamp}` to the sending
  connection only. The ack is sent after the commit and before the frame is fanned out.
- `clientId` is stored as the activity's idempotency key, under the unique index on
  `(conversation_id, idempotency_key)` that the REST `X-Idempotency-Key` header already uses
  (**Implemented** for REST). A retransmitted `clientId` is not stored again: the server answers
  with the original ack plus `duplicate: true`. The dedupe window is therefore the lifetime of
  the activity (at least 24 hours is the guarantee clients may rely on).
- A rejected send is answered with `error` carrying the same `clientId` and is not persisted.
  Retryable errors (`rate_limited`, `too_many_in_flight`, `unavailable`) MAY be retried with the
  **same** `clientId`; non-retryable ones MUST NOT be.
- At most `limits.maxInFlight` (32) sends per connection may be unacked; more draw
  `too_many_in_flight`. A client that reconnects re-sends its unacked sends with their original
  `clientId`s after `welcome`.
- A send without `clientId` but with an `id` (mekik/1 and chativa clients stamp every outgoing
  message with one) is treated as if `clientId` were that `id`, provided it matches the
  `clientId` syntax above: unmodified mekik/1 clients therefore also get exactly-once persistence
  and an `ack` (which they ignore by the unknown-frame rule). If both are present, `clientId`
  wins.
- A send with neither (or with an `id` that does not match the syntax) gets no ack and is
  persisted once per frame received.

```json schema=frames/server/ack.schema.json
{ "type": "ack", "clientId": "c-17", "id": "a2f7d9e4-3b1c-4d5e-8f9a-0b1c2d3e4f50", "seq": 18, "timestamp": 1750000004000 }
```

Sends into a closed conversation are refused with `conversation_closed` (**Implemented** on
`postActivity`, the legacy socket and REST, HTTP 409); the conversation must be reopened first.

## 8. Receipts, typing, presence, heartbeat

### 8.1 deliveryStatus: **Planned (#25)**

Converger tracks a delivery per activity and target channel (**Implemented**:
`Converger.Deliveries`; the WebSocket channel currently ignores the `delivery_status` broadcast).
v1 pushes it as `deliveryStatus`, to every connection of the conversation except end-user connections
that did not send the activity. Statuses only move forward: `queued`, `sent`, `delivered`, `read`;
`failed` is terminal for that attempt series.

```json schema=frames/server/deliveryStatus.schema.json
{ "type": "deliveryStatus", "data": { "activityId": "a2f7d9e4-3b1c-4d5e-8f9a-0b1c2d3e4f50", "seq": 18, "channelId": "wa-main", "status": "delivered", "timestamp": 1750000005000 } }
```

A client marks everything up to a seq as read with `read {watermark}`. The server stores the
participant's read watermark (it never moves backwards), forwards it to channels that support
read receipts, and sends `deliveryStatus {upToSeq, status: "read", by}` to the other participants.

```json schema=frames/client/read.schema.json
{ "type": "read", "watermark": 18 }
```

### 8.2 typing: **Planned (#25)**

`typing {isTyping}` is transient in both directions and flat, as chativa's `parseChatFrame`
expects. The server relays it to the conversation's other connections and to target channels that
support it, adding `from` and `sender`. A client sends at most one per 2 s; an indicator that is
not refreshed within 6 s expires. Today typing is an activity type that is persisted; with #25 it
stops being stored.

```json schema=frames/server/typing.schema.json
{ "type": "typing", "isTyping": true, "from": "bot", "sender": { "id": "agent-7", "role": "agent" } }
```

### 8.3 presence: **Planned (#25)**

`presence {participant, status, connections?}` is derived from the participant's live connections
across nodes (Phoenix Presence, already used for socket tracking in `ConvergerWeb.SocketPresence`).

### 8.4 conversationUpdate

A persistent frame for lifecycle and membership changes. **Implemented** as an activity: closing,
expiring and reopening a conversation emits a `conversationUpdate` activity with sender `system`.
Delivered as a v1 frame with #22; participant changes are #25.

```json schema=frames/server/conversationUpdate.schema.json
{ "type": "conversationUpdate", "id": "0b9a6c3e-2d4f-4e5a-8b7c-9d0e1f2a3b4c", "seq": 30, "from": "bot", "sender": { "id": "system", "role": "system" }, "data": { "event": "conversation_closed", "status": "closed", "reason": "expired" }, "timestamp": 1750000009000 }
```

### 8.5 heartbeat and idle timeout: **Planned (#22)**

The server sends `heartbeat` after `heartbeatIntervalMs` (30 s) of outbound silence and in answer
to `ping`. A client sends `ping` after `idleTimeoutMs / 2` of its own silence. A connection with no
inbound frame for `idleTimeoutMs` (60 s) is closed with **4408**. WebSocket ping/pong control frames
also count as activity.

```json schema=frames/server/heartbeat.schema.json
{ "type": "heartbeat", "timestamp": 1750000031000, "nonce": "p-3", "headSeq": 18 }
```

## 9. The bot channel and mekik relay: **Planned (#64)**

A conversation can have a bot channel speaking mekik/1 (a mekik server behind Converger, connected
over a channel-scoped socket, section 10). For that conversation:

- client `resume`, `genui_event`, `client_tools`, `client_skills`, `abort`, `survey`, `regenerate`,
  `edit` and `meta` are forwarded to the bot channel unchanged;
- the bot's transient frames (`run`, `typing`, `genui_components`, `skills`, `error`) are relayed
  to the conversation's connections, and its persistent frames are stored, renumbered into the
  conversation's seq space and fanned out;
- the **turn lock is the bot's**: Converger does not serialise turns. A bot's `error` `busy`,
  `interrupted`, `not_interrupted` or `incomplete_resume` is relayed to the connection whose frame
  caused it;
- a message from a non-mekik channel (for example a tapped WhatsApp button) that answers an open
  `interrupt` is converted to `resume` for the bot channel ([messages.md](./messages.md), section 6).

If the conversation has no bot channel, the bot-only frames draw `error` `bot_unavailable`.

## 10. Channel-scoped sockets: **Planned (#64, #67)**

A token with `scope: "channel"` opens a connection that sees **every conversation of its channel**:
agent consoles, the `@converger/agent` SDK (#67) and the mekik transport (#64).

- `welcome` has `scope: "channel"` and `channelId`, and no `conversationId`, `userId`, `watermark`
  or `pending`.
- Connection-level frames (`hello`, `welcome`, `auth`, `tokenRefreshed`, `ping`, `heartbeat`, and
  `error` about the connection) are sent bare.
- Every conversation-level frame, in both directions, is wrapped as `{conversationId, frame}`. The
  envelope has no `type`; that is how a receiver tells it apart from a bare frame.
- Live frames of every conversation of the channel are delivered. To resume, a client lists
  per-conversation watermarks in `hello.watermarks`, or sends an enveloped `sync` later.
  Conversations not listed start live; the client discovers missed conversations over REST.
- Acks, errors and receipts about one conversation are enveloped with its `conversationId`.
- A connection follows at most `limits.maxConversations` conversations at once (default 5000);
  beyond that the server answers `too_many_subscriptions` and stops delivering live frames for
  the least recently active conversations.

```json schema=frames/channel/server-envelope.schema.json
{ "conversationId": "c0a8012e-7d3b-4c5e-9f1a-2b3c4d5e6f70", "frame": { "type": "text", "id": "msg-9", "seq": 19, "from": "user", "data": { "text": "Where is my order?" }, "timestamp": 1750000004000 } }
```

```json schema=frames/channel/client-envelope.schema.json
{ "conversationId": "c0a8012e-7d3b-4c5e-9f1a-2b3c4d5e6f70", "frame": { "type": "text", "clientId": "agent-c-3", "data": { "text": "Let me check that for you." } } }
```

## 11. Limits

Values are defaults; the server announces the effective ones in `welcome.data.limits`.

| limit | default | today | on violation |
| --- | --- | --- | --- |
| `maxFrameBytes`, one inbound frame | 128 KiB | **Implemented** on the Phoenix sockets (`WS_MAX_FRAME_BYTES`, #27) | `payload_too_large`; above 1 MiB the socket is closed with 1009 |
| inbound frames per connection | 20 per second | **Implemented** on the Phoenix sockets (`WS_MAX_MESSAGES_PER_WINDOW`, #27) | `rate_limited` with `retryAfterMs` |
| joined channels per Phoenix socket | 50 | **Implemented** (`WS_MAX_JOINS`, #27) | `too_many_joins` reply |
| outbound frames buffered for a slow client | 1 000 | **Implemented** (`WS_SLOW_CONSUMER_QUEUE_LEN`, #27) | close 4503 `slow_consumer` |
| `maxTextBytes`, `data.text` | 64 KiB | **Implemented** (`activity_limits.max_text_bytes`) | `payload_too_large` |
| `maxMetadataBytes`, `metadata` as JSON | 16 KiB | **Implemented** (`max_metadata_bytes`) | `payload_too_large` |
| attachments (legacy `text.data.attachments`) | 10 items, 4 KiB each | **Implemented** | `invalid_message` |
| `extensions` in message data | 8 KiB | Planned (#28) | `payload_too_large` |
| `maxInFlight`, unacked sends per connection | 32 | Planned (#24) | `too_many_in_flight` |
| `heartbeatIntervalMs` | 30 000 | Phoenix heartbeat today | - |
| `idleTimeoutMs` | 60 000 | Phoenix default today | close 4408 |
| `replayBatch` | 100 | **Implemented** (`ws_replay_limit`, `PAGINATION_WS_REPLAY_LIMIT`) | - |

| sends per tenant | `activity_create` bucket | **Implemented** for REST (429 + `Retry-After`); WebSocket sends are limited per connection (above) | `rate_limited` with `retryAfterMs` |
| typing frames per connection | 1 per 2 s | Planned (#25) | dropped silently |

## 12. Errors

### 12.1 The error frame

mekik/1 `error {data: {code, message}}`, sent only to the connection that caused it, plus Converger
fields: `number` (stable numeric code), `retryable`, `retryAfterMs`, `clientId` and `frameType`
(what the error answers) and `details` (for example validation errors per field, as the REST API
returns them). Codes relayed from a bot channel are passed through unchanged.

```json schema=frames/server/error.schema.json
{ "type": "error", "data": { "code": "rate_limited", "message": "too many messages", "number": 3000, "retryable": true, "retryAfterMs": 1500, "clientId": "c-17", "frameType": "text" } }
```

### 12.2 Error codes

The string `code` is the stable key; `number` is stable too and groups codes by range. REST
equivalents are given for codes the API shares.

| code | number | retryable | closes | REST | meaning |
| --- | --- | --- | --- | --- | --- |
| `bad_request` | 1000 | no | no | 400 | malformed JSON, unknown type, missing or mistyped field (mekik/1) |
| `no_session` | 1001 | no | no | - | frame before `hello`, or after disconnect (mekik/1) |
| `unsupported_protocol` | 1002 | no | 4400 | - | `hello.protocol` names a version the server does not speak |
| `invalid_watermark` | 1003 | no | no | - | watermark above the head, or a legacy form after the migration window |
| `invalid_message` | 1004 | no | no | 422 | the message failed validation (`details` per field) |
| `unauthorized` | 2000 | no | 4401 | 401 | missing or invalid credential (mekik/1) |
| `token_expired` | 2001 | yes, after refresh | 4401 | 401 | the session's token expired |
| `forbidden` | 2002 | no | no | 403 | the token's scope does not allow the frame or conversation |
| `channel_inactive` | 2003 | no | 4403 | 400 | the channel was deactivated |
| `rate_limited` | 3000 | yes | no | 429 | rate limit hit; wait `retryAfterMs` (REST: `Retry-After`) |
| `payload_too_large` | 3001 | no | no (1009 above the hard cap) | 413 | a size limit was exceeded |
| `too_many_in_flight` | 3002 | yes | no | - | more than `maxInFlight` unacked sends |
| `too_many_subscriptions` | 3003 | no | no | - | channel-scoped socket follows too many conversations |
| `slow_consumer` | 3004 | yes | 4503 | - | the client reads too slowly; reconnect after `retryAfterMs` and resume from the watermark |
| `conversation_closed` | 4000 | no | no | 409 | the conversation is closed; reopen it first |
| `conversation_not_found` | 4001 | no | no | 404 | unknown conversation, or not visible to the token |
| `busy` | 5000 | yes | no | - | relayed from the bot: a run is in flight (mekik/1) |
| `interrupted` | 5001 | no | no | - | relayed: answer the open interrupt first (mekik/1) |
| `not_interrupted` | 5002 | no | no | - | relayed: `resume` with no open interrupt (mekik/1) |
| `incomplete_resume` | 5003 | no | no | - | relayed: `resume` missed an open interrupt (mekik/1) |
| `bot_unavailable` | 5004 | yes | no | - | the frame needs a bot channel and there is none, or it is unreachable |
| `internal` | 9000 | yes | no | 500 | unexpected server error (mekik/1 TS transport) |
| `unavailable` | 9001 | yes | 1012 | 503 | the node is draining; reconnect, possibly elsewhere (**Implemented**, #27) |

Retryable means the same frame (with the same `clientId`) may be sent again later.

### 12.3 Close codes

| code | when |
| --- | --- |
| 1000 | normal close |
| 1009 | inbound frame above the hard size cap |
| 1011 | internal error |
| 1012 | server restart or node draining: reconnect with backoff and the same watermark |
| 4400 | unsupported protocol |
| 4401 | `unauthorized` or `token_expired` (mekik/1 `AUTH_CLOSE_CODE`) |
| 4403 | `channel_inactive`, or the socket was force-disconnected (`ConvergerWeb.Sockets`) |
| 4408 | idle timeout |
| 4503 | `slow_consumer`: too many frames buffered for the client |

1012 and 4503 carry a JSON close reason, `{"reason": "unavailable" | "slow_consumer", "retryAfterMs": N}`, with a
jittered `N` (**Implemented** on the Phoenix sockets, #27; see
[WebSocket limits and draining](../operations/websocket-limits.md)).

Clients SHOULD reconnect with jittered exponential backoff on every code except 4400, and on 4401
only after obtaining a new token.

## 13. Compatibility and deprecation

### 13.1 Within v1

Only additive changes: new optional fields, new frame types, new message types, new error codes,
new capabilities. Receivers ignore what they do not know, so these never break a peer. Every
addition updates this document and the schemas in the same change.

### 13.2 A future v2

A breaking change creates `converger/2`, negotiated by the subprotocol `converger.v2` (and
`hello.protocol`). A server supports v1 and v2 side by side for at least 12 months after v2 ships;
`welcome.data.compat` lists what the server still speaks.

### 13.3 Deprecation of the pre-v1 surfaces

| surface | status | removal |
| --- | --- | --- |
| `/socket` `conversation:*` topic (`ConvergerWeb.UserSocket`, `new_activity`, `last_activity_id`) | **deprecated** (#23) | no earlier than two minor releases and 6 months after #23 |
| legacy tokens: `POST /api/v1/tokens`, channel tokens in `x-channel-token` (incl. `POST /api/v1/conversations`) | **deprecated** (#23) | same window as above |
| `activitySet {activities, watermark, has_more}` and `postActivity` on `converger:conversation:*` (join without `protocol`) | deprecated when #22 ships | same window as above |
| opaque base64url watermarks | accepted for one release after #22 (section 6.5) | the following minor release |

Deprecated surfaces log a warning per connection (per request for HTTP, which also carries the RFC 9745
`Deprecation` and `Link: <...>; rel="deprecation"` headers), emit the telemetry event
`[:converger, :deprecated, :use]`, and are announced in the changelog when they are deprecated and again one release
before removal.

## 14. mekik/1 compatibility

Converger Protocol v1 is a superset profile of mekik/1. Each mekik/1 frame:

| mekik/1 frame | direction | Converger v1 | notes |
| --- | --- | --- | --- |
| `hello` | c2s | **extended** | all mekik/1 fields unchanged; adds `protocol`, `watermarks` (channel scope); `watermark` also accepts legacy forms during migration |
| `text` (user turn) | c2s | **extended** | adds optional `clientId`, `metadata`, `replyTo`; same frame family carries every message type |
| `resume` | c2s | **adopted** | forwarded to the bot channel; replay-from-watermark is `sync` |
| `genui_event` | c2s | **adopted** | forwarded |
| `client_tools` | c2s | **adopted** | forwarded; Converger does not interpret declarations |
| `client_skills` | c2s | **adopted** | forwarded |
| `abort` | c2s | **adopted** | forwarded |
| `survey`, `regenerate`, `edit` (chativa connector) | c2s | **adopted** | forwarded; gated by `welcome.data.capabilities` |
| `welcome` | s2c | **extended** | `protocol: "converger/1"`, `compat: ["mekik/1"]`; adds `scope`, `channelId`, `expiresAt`, `capabilities`, `limits`; `watermark` is the head seq |
| `text` | s2c | **extended** | adds optional `sender`, `metadata`, `clientId`; `from` stays `user` or `bot` |
| rich message frames (section 4.5) | s2c | **adopted** | the open rule is unchanged; Converger adds typed schemas for the vocabulary in [messages.md](./messages.md) |
| `tool_call` | s2c | **adopted** | byte-identical; `seq` renumbered into the conversation seq space |
| `skill` | s2c | **adopted** | as `tool_call` |
| `genui` | s2c | **adopted** | as `tool_call` |
| `interrupt` | s2c | **adopted** | as `tool_call`; answers from non-mekik channels become `resume` |
| `interrupt_resolved` | s2c | **adopted** | as `tool_call` |
| `genui_components` | s2c | **adopted** | relayed after `welcome` |
| `skills` | s2c | **adopted** | relayed after `welcome` |
| `run` | s2c | **adopted** | relayed from the bot channel |
| `error` | s2c | **extended** | adds `number`, `retryable`, `retryAfterMs`, `clientId`, `frameType`, `details`; adds hub codes (section 12.2) |
| `typing` (chativa) | s2c | **extended** | also sent by clients (c2s); adds `from` and `sender` |
| turn lock, `busy`, `interrupted` semantics (section 5) | - | **not applicable** | owned by the bot; Converger only relays the errors |
| backplane envelope (section 5.1) | - | **not applicable** | node-to-node inside mekik; Converger uses Phoenix PubSub |
| MCP and A2A doors (sections 13, 14) | - | **not applicable** | not WebSocket frames; a mekik bot keeps serving them itself |
| auth close 4401 (section 7) | - | **adopted** | also used for `token_expired`; mid-session refresh is an addition |
| query-string identity (section 1, section 7) | - | **adopted** | hints for L7 affinity; the token decides |

Additions without a mekik/1 counterpart: `ack`, `deliveryStatus`, `presence`,
`conversationUpdate`, `event`, `heartbeat`, `tokenRefreshed`, `replayTruncated`, client `read`,
`sync`, `ping`, `auth`, and the channel-scoped `{conversationId, frame}` envelope. A mekik/1
client never sends `clientId`, but the `id` it stamps on outgoing messages is used as one
(section 7), so its sends are de-duplicated and acked; it ignores the `ack` and the other
additions by the unknown-frame rule.

The persistent frames of mekik's golden fixtures (`conformance/fixtures/*.json`) are vendored in
`test/protocol/fixtures/mekik/` and validated against the Converger schemas by the conformance
suite. Their storage round trip (stored and re-read byte-identically, canonical JSON) is part of #28.

## 15. Conformance

`test/protocol/` (tag `:protocol`, part of the normal test run) checks that:

- every schema in `priv/protocol/v1` builds and its `examples` validate, directly and through the
  direction dispatchers `server-frame.schema.json` and `client-frame.schema.json`;
- every frame of the example sessions in `priv/protocol/v1/examples/` validates, and the frames in
  `examples/invalid.json` are rejected;
- every JSON block annotated with a schema in this document and in [messages.md](./messages.md)
  validates (fenced as `json schema=PATH`);
- mekik/1's golden fixture frames are valid Converger server frames with contiguous `seq`.

Implementation issues (#22 to #28, #64) extend the suite with live round trips against the server:
connect, handshake, replay, ack, dedupe and gap fill.
