# Backbone matrix

How the event backbone ([ADR-0070](../adr/0070-pluggable-event-backbone.md)) changes the numbers of the
[load harness](index.md): every scenario on the Native backbone (Phoenix.PubSub + Oban on Postgres) and on Kafka,
with one and three nodes. The `backbone` rows are the [backbone zero-loss check](index.md#backbone-zero-loss-check):
every activity of the run is published to the backbone, and a platform webhook subscriber must observe each one
exactly once.

:::caution Pending
No numbers are published here yet. They must come from a quiet machine or the nightly runner: the harness was
built and smoke-tested (both backbones, one node, short profile) on a developer machine that was running other
workloads at the same time, so those timings are not representative and are not shown.

The table below is filled in by the nightly `Load` workflow (its `matrix` job opens a pull request with this page
regenerated), or by hand on a quiet machine with:

```bash
LOAD_MATRIX_PUBLISH=1 load/matrix.sh
```

(`native` and `kafka` x 1 and 3 nodes, full profile, about two hours; see [Backbone matrix](index.md#backbone-matrix).)
:::

## What the table contains

One column per backbone and topology (`1 node, native`, `3 nodes, native`, `1 node, kafka`, `3 nodes, kafka`), and
per scenario:

| Scenario | Numbers |
| --- | --- |
| `e2e` (REST → WebSocket fan-out) | p50 / p95 / p99 latency, REST POST p95, sustained acked msgs/s, frames/s, connections |
| `webhook_burst` (inbound burst fanned out to three channels) | accepted/s, inbound POST p95, inbound → provider p50 / p95 / p99, deliveries/s, drain time |
| `idle` (10 000 idle sockets) | connections, connect p95, memory per idle socket |
| `reconnect_storm` | reconnect p95 / max, REST → WebSocket p95 during storms |
| `rolling_restart`, `node_kill` | node back to ready (recovery time), client reconnect max |
| `backbone` | events observed / expected, duplicate events, send → subscriber p50 / p95 / p99, catch-up time |
| every scenario | **lost acked messages** (must be 0), CPU and RSS per node and for the Kafka broker, DB pool waits, Oban queue depth |

The hardware profile of each run (vCPUs and memory visible to Docker, OS, kernel, Docker and Postgres versions,
per-node limits, pool sizes) is recorded under the table.
